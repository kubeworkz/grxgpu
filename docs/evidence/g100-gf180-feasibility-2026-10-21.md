## Frontend result and disposition

The first invocation stopped immediately because the file list used paths relative to the wrong working directory. The next run used absolute paths but listed all sources alphabetically, placing `VX_dxa_pkg.sv` before its imported `VX_gpu_pkg`. Surelog then reported `[ERR:EL0514]` in the DXA package for `LMEM_DMA_ADDR_WIDTH`, which is defined in the GPU package. A package dependency audit of the generated set confirmed that `VX_dxa_pkg`, `VX_fpu_pkg`, and `VX_tcu_pkg` import `VX_gpu_pkg`; no package in that set imports any of those three. Thus the dependency order is `VX_gpu_pkg` first, followed by the other packages, then interfaces and remaining sources. RTL was not modified.

An independent 3,600-second-bounded rerun on the exact generated 128-core source set used absolute paths and the dependency-ordered package-first list. Surelog entered `[INF:EL0526] Design Elaboration...`, emitted no repeat of the `LMEM_DMA_ADDR_WIDTH` diagnostic, and proceeded into a very large expansion of TCU arithmetic generate blocks. It ended at the 3,600-second timeout (`frontend_exit=124`) before `hierarchy -check`, `prep`, `check -assert`, or the RTLIL/JSON writes; no elaboration pass is claimed. At timeout, the main Yosys process had been using roughly 4.5–4.9 GiB RSS, and each of stdout and Surelog logs was about 723 MiB. The run wrapper has since completed and the working tree is idle.

The rerun therefore resolves the observed package-order diagnostic, but full frontend/elaboration remains blocked by the cost of expanding this configuration with the pinned Synlig/Surelog frontend within one hour. It does not establish whether a longer runtime, more memory, or a different frontend strategy would complete.

## Frontend phase isolation follow-up (2026-10-22)

The corrected one-hour run's console trace contains both `Surelog preproc status: 0` and `Surelog parsing status: 0` before it stops. It completed in 138 seconds (79.30 user / 10.39 system seconds; 1.44 GiB maximum RSS), reported zero fatal/syntax/error diagnostics and 260 warnings (no timescale), and reported about 71.6 seconds preprocessing and 65.0 seconds parsing. However, this was not a complete design elaboration test: Surelog's run returned after emitting no elaboration profile/summary or UHDM artifact. It establishes that preprocessing/parsing can complete quickly, but not that Surelog elaboration is fast.

A Synlig/Yosys `read_systemverilog -parse-only` probe using the full manifest reached both successful Surelog preprocessing/parsing status messages, then timed out at five minutes while the encompassing Synlig frontend command remained active. It did not reach hierarchy or output generation; peak RSS was 1.31 GiB. This is not a clean parser-only measurement: the option still runs Synlig frontend work, and those Surelog status messages do not imply that Surelog has finished all processing or that Synlig has consumed its result. The probe also used a fresh frontend work area.

**Diagnosis:** the 65-minute original run and the 10-minute monitored rerun both stall after Surelog reports preprocessing and parsing success. The monitored rerun localizes the long post-parse portion to the Yosys parent process after its Surelog child has returned: the child was still active at the first one-minute sample (8 seconds elapsed, 57.2% CPU, 195 MiB RSS), but was absent by the second sample; Yosys then remained alive with RSS growing from 34 MiB at 1 minute to 3.01 GiB at 9 minutes. Its log remained at `Executing Verilog with UHDM frontend`, with no frontend completion, `Generating RTLIL representation`, hierarchy pass, or netlist output. This is consistent with Synlig/Yosys consuming or processing Surelog's UHDM result, rather than Surelog itself remaining active for most of the budget, but the available logs do not identify the exact Yosys/Synlig routine. Memory pressure is material: the sample reached 3.0 GiB RSS on a WSL instance with about 5.8 GiB total memory. The Yosys process was in uninterruptible `D` state at two samples, so I/O and swapping may also contribute. Importantly, this probe actually ran under `/mnt/c/...` on the Windows-backed WSL filesystem, not WSL-native ext4; filesystem behavior is therefore a confounder.
